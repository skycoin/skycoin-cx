# Conventions

Every rule of this repository in one list. Each item links to its detailed
document or check script.

1. **Tiers.** Every Go package sits one level below the root as
   `t<N>-<name>`, where N is 1 plus the highest tier it imports. `make
   check-tiers` runs [check-tiers.sh](../check-tiers.sh). See the layout
   section of the [README](../README.md#repository-layout).
2. **Explicit Init.** No `func init()` outside package main. Setup is an
   exported Init function that `t11-cx` main calls in order. `make
   check-inits` runs [check-inits.sh](../check-inits.sh) against
   [init-allowlist.txt](../init-allowlist.txt), which only shrinks.
3. **No interface embedding.** An interface lists its methods and never
   embeds another interface. `make check-ifaces` runs
   [check-ifaces.sh](../check-ifaces.sh) against
   [iface-allowlist.txt](../iface-allowlist.txt).
4. **No recover.** No code outside `vendor/` calls `recover`. `make
   check-recovers` runs [check-recovers.sh](../check-recovers.sh) against
   [recover-allowlist.txt](../recover-allowlist.txt).
5. **Two classes of error.** Path, file and network failures return their
   module's error struct, and every other failure is a crashing assert from
   `t0-cx-core-assert`. See [ErrorHandling.md](ErrorHandling.md).
6. **Naming.** Self describing, hierarchical, lexicographically prefixed
   names in Java type name style. See the Naming section of
   [AGENTS.md](../AGENTS.md#naming) and
   [skycoin-cx#212](https://github.com/skycoin/skycoin-cx/issues/212).
7. **Opcode numbers are fixed.** Every opcode has a fixed number in
   `constants.OpcodeLifecycleTable` in
   [t1-constants/opcodes.go](../t1-constants/opcodes.go), mirrored in
   [opcodes.csv](opcodes.csv). A new opcode takes the next number after the
   highest. A deleted opcode keeps its row as deprecated, gets no handler, and
   its number is never reused before the row's reassignable version.
8. **Opcode lifecycle.** Each row records the version the number was added,
   deprecated and becomes reassignable, 0 for the last two while live and 0
   added for opcodes older than versioning. Reassignable is the deprecated
   version plus one year (`OpcodeReassignmentIntervalYears`), same month and
   day, release 0001, so deprecated 2611200001 is reassignable from
   2711200001, and 29 February moves to 1 March. Every event is listed in
   order in [t1-constants/opcodes_history.go](../t1-constants/opcodes_history.go).
   A renamed opcode keeps its number and row, which takes the new name, and
   `constants.OpcodeRenameTable` records the old name and the version as a
   `renamed` event. An old name is a compile error and is never reused.
   `go test ./t1-constants` fails when the table, the CSV and the history
   disagree.
9. **Language version.** The integer `yymmddnnnn`, the release date and the
   release number that day, for example 2611200001 is 2026-11-20 release
   0001. `constants.LanguageVersionCurrent` is stored in every serialized
   program and `Deserialize` rejects any other version. See the Language
   versions section of [LanguageGuide.md](../LanguageGuide.md#language-versions).
10. **Branching.** `main` is the only long-lived branch. One branch and one
    pull request per change, merged into `main` after the `check` jobs pass.
    See [CONTRIBUTING.md](../CONTRIBUTING.md#git-branching-model).
11. **Changelog.** Every user visible change adds a line under `Unreleased`
    in [CHANGELOG.md](../CHANGELOG.md) with its issue or pull request number.
12. **Compiler IR.** What the compiler emits, the in-memory program and its
    serialized form, is described in [IR.md](IR.md). A change to the IR or
    the serialized form updates it.
13. **Object model.** Every IR object type has a Def file, an `<Obj>Mng`
    manager that is the only place objects are allocated and released, and
    an `<Obj>Gid` generational index. One `CxIrState` owns every manager,
    no pointer to an object is kept at rest, and every manager's Len is 0
    after teardown. Files are named `<obj>_def.go`, `<obj>_mng.go`,
    `<obj>_gid.go`, `<obj>_fon.go` and `<obj>_fof.go`. The Gid and manager
    files are generated by `make generate-objmodel`, and `make
    check-objmodel` runs [check-objmodel.sh](../check-objmodel.sh). See
    [ObjectModel.md](ObjectModel.md).
14. **Built-in libraries live under `sys/`.** A library implemented inside
    the compiler and runtime is a system library named `sys/<name>`, for
    example `sys/string`. It is marked as built in where it is documented,
    and a program must still import it explicitly (`import "sys/string"`).
    Using a `sys/` package without the import, or importing it without
    `sys/`, is a compile error. Its functions have verbose upper camel case
    names, for example `string.OrderingByByteValue`, and are never exposed
    as operators. `packages.DefaultPackages` in t0-packages lists them. See
    #380 and #379.
15. **GC reach.** The vm executor (`t3-cx-runtime-vm`) and the IR base
    (`t2-cx-runtime-ir`) never import t3-ast or the collector
    (`t2-cx-runtime-gc`), which only t3-ast imports. Every other place that
    allocates on the heap, ticks the collector or touches a GC root table
    has a two line `GCREACH:` comment above it or above its function. `make
    check-gcreach` runs [check-gcreach.sh](../check-gcreach.sh). See
    [GarbageCollector.md](GarbageCollector.md).
16. **System libraries.** File access, networking, processes and the hash and
    signatures of `sys/cipher` (see [CipherLibrary.md](CipherLibrary.md))
    are system libraries, never rows of the opcode table. A program calls one through
    the single opcode `LibraryCall` with a library number and a function
    number, and the run checks at every call that the library is enabled.
    Library numbers (`constants.LibraryTable`) and the function numbers of
    each library (`constants.LibraryFunctionLifecycleTable`) in
    [t1-constants/libraries.go](../t1-constants/libraries.go) follow rules 7
    and 8: fixed for life, a new one takes the next number, a deleted one is
    deprecated and not reused before its reassignable version, 0 is never
    assigned. `constants.LibraryPolicyEnabledWhenImported` is the default
    for a library `--enable` does not name. See the System libraries section
    of [LanguageGuide.md](../LanguageGuide.md#system-libraries) and #492.
17. **Variable scoping.** A name in a function body is a local, a
    parameter or result, or a global the function declares, and nothing
    else. Every function lists the globals it uses in a `global`
    statement at the top of its body, its own package's included, and
    reaches a global of another package as `package.name` or through an
    import into scope. No name may shadow another: a local, parameter,
    result, loop variable or `:=` name never has the name of a global, an
    imported package, a function or a type of its package, or a variable
    of an enclosing block. The compiler keeps the statements in
    `t4-actions/scope_globals.go`, checks each use where a body resolves
    a global (`GetGlobalSymbol`) and each declaration where it enters the
    symbol table (`UpdateSymbolsTable`).
    `import "pkg"` reaches the members of `pkg` only as `pkg.name`. An
    import into scope, `import . "pkg"` or `import (a, b) "pkg"` for the
    package and `import file . "pkg"` or `import file (a, b) "pkg"` for
    its file, adds the names as shorthands that compile to `pkg.name`. A
    name brought into scope never masks a local, parameter, result,
    global, function, type, imported package or name of another import.
    Masking is a compile error, and a warning in a function under a
    `//cx:masking warning` directive on the line before it. The compiler
    keeps the imports in `t4-actions/scope_imports.go`, resolves a
    shorthand where a body names an identifier (`PrimaryIdentifier`) or
    a type (`DeclarationSpecifiersStruct`), and checks masking once the
    declarations of a package are known (`ImportScopedCheck`) and where a
    local enters the symbol table. See the Global variables, Scopes and
    shadowing and Imports into scope sections of
    [LanguageGuide.md](../LanguageGuide.md), #486 and #487.
18. **Strings on the run path.** The old loop does no string operation
    on its run path outside printing, failure branches and the boundaries
    to Go and the OS. Every one it can reach has a `VIOLATION STRHOT-nnn:`
    comment above it or above its function, with the code and class of
    [strhot-codes.txt](../strhot-codes.txt). `make check-strhot` runs
    [check-strhot.sh](../check-strhot.sh). See
    [StringsHotPath.md](StringsHotPath.md) and #412.
19. **Execution records.** Every program of `tests/` is either an execution
    record in [tests/execution-records.txt](../tests/execution-records.txt),
    its program, input and output hashes and exit code, or excluded there
    with a reason. `TestExecutionRecords`, part of `make check`, runs each
    record on the old loop, vm, the round trip through the image and the
    built executable and fails on any other result. `make records` writes
    the file from the old loop and is never part of `make check`. See
    [ExecutionRecords.md](ExecutionRecords.md) and #507.
